# IAM channel and the Applications page

Goal
  A member of a deployment sees the applications (OAuth clients) of a realm in the Identity space, through a channel that reads FerrisKey without Autharie's control plane ever holding the content. The channel is built for every later IAM page (users, organisations, roles); Applications is its first user, read-only.

Context
  ADR 0014 gave Identity a place; ADR 0015 decided how it reads FerrisKey: one request at a time through the data plane, the answer sealed to the browser that asked. This is that channel's first slice. The existing pieces it reuses: the registry's sealed credential (ADR 0013, `docs/specs/agent-registry.md`: key generated by the browser, one delivery, deletion after delivery or expiry), the action and outcome path of webhooks and SMTP, and the operator's admin client (`ferriskey_admin.rs`, `ferriskey_clients.rs`).
  Defaults below marked (to confirm) are answers to the spec questions, taken as recommended until the owner says otherwise.

Glossary
  IAM request: one operation on one realm of one deployment, asked by one member, answered once. Rejected: "query", "call" (writes will use it too).
  IAM operation: a named, typed operation the control plane accepts (`applications.list`, `applications.get`). Never a FerrisKey path.
  Sealed result: the operation's answer as a hybrid envelope for the key the browser generated for that request.
  Application: Autharie's word for a FerrisKey client, as the console already says "Applications" in the Identity tabs.

Invariants
  - Only named operations exist; a request for anything else is refused before it is recorded.  [type: `IamOperation` enum; `access()` says Read or Write]
  - The control plane, Herald, the bus and the IdentityInstance never hold a result in clear: the control plane stores the envelope, the operator is the last place that sees the content before the browser.  [test]
  - A client's `secret` never appears in any result, sealed or not: the operator drops it before sealing.  [test]
  - A result is sealed to the request's key and bound to the request: an envelope for request A does not open as request B.  [test: AAD = request id]
  - An envelope is handed out once, then deleted; one not fetched within 5 minutes is deleted. A tombstone without content answers 410 until expiry.  [test]
  - A result larger than 512 KiB is refused, never cut; a page holds at most 50 objects.  [type: `PageSize`; test]
  - Every request leaves an audit entry (who, operation, realm, request id, time) and never the result.  [test]
  - Reading needs VIEW_INSTANCES; an operation whose `access()` is Write will need MANAGE_INSTANCES. Only FerrisKey deployments accept requests.  [test]
  - A request id is executed at most once by the operator, even if its action is redelivered.  [test]
  - A deployment has at most 10 requests not yet delivered or expired; the 11th is refused with 429.  [test]
  - A search term is personal data: it is kept out of the audit entry and out of the action listings, and lives in the action row only until the action's own retention ends.  [test]

Out of scope
  - Creating, editing, deleting or rotating an application (next slice, with the secret handling of ADR 0013 reused).
  - Users, organisations and roles pages.
  - New permission bits for IAM, and delegated (SSO) access: that is ADR "delegated access".
  - Lowering Herald's poll interval: its own change to the chart, before or beside this work.
  - Search as-you-type, cross-realm search, counts for the realm overview.

Design
  Control plane (libs/autharie-domain/src/iam/, libs/autharie-postgres/src/iam/, libs/autharie-api/src/handlers/deployments/iam.rs)
    - `IamOperation` (enum) with `ApplicationsList { page, limit: PageSize, search: Option<SearchTerm> }` and `ApplicationsGet { id: Uuid }`; `access()`.
    - `IamRequest { id, deployment_id, realm, operation, actor, sealing_key: SealingKey, state: Pending | Done | Failed | Delivered, sealed: Option<Envelope>, message, created_at, expires_at }`.
    - Table `iam_requests`; a tombstone row after delivery until `expires_at`.
    - Use cases: ask (validate, audit, record the action), poll (202 pending, 200 once, 410 delivered, 404 expired), record outcome.
    - Action `deployment.iam.request` (v1).
    - Outcome `kind: "iam"` ingested like `smtp` and `deployment.agents`.
  Data plane
    - CRD IdentityInstance: `spec.iamRequests[] { requestId, realm, operation, sealingKey, expiresAt }`; `status.iam.requests[] { requestId, phase, message? }`. No content in the resource.
    - Genesis: handler writes the request entry; the status watcher, when a request finishes, reads the sealed result from Secret `<instance>-iam-results` (key `<requestId>`) and publishes the outcome, then asks for the entry and key to be removed.
    - Operator: runs each unseen request against the admin API (`GET /realms/{realm}/clients?page&limit&search`, `GET /realms/{realm}/clients/{id}`), maps to the result below dropping `secret`, seals it, writes the Secret key, sets the phase. Drops expired entries.
  Console (apps/console/src/domain/identity/iam/, domain/applications/)
    - `sealing`: RSA-OAEP-256 key pair (non-extractable private key, memory only) and the envelope opener.
    - `useIamRequest(operation)`: generates the key, POSTs, polls every 3 s up to 90 s, decrypts, returns a typed result; shows "this is taking longer than usual" past 20 s.
    - Applications page at `identity/realms/$realm/applications`: table (name, client id, type, enabled, source), search submitted with Enter, next page, a row opens `applications/$id` with the read-only detail. Clients created by Autharie (`agent-*` registered from the Agents tab) carry an "Agent" badge pointing to the Agents tab (to confirm). The Applications tab stops being "Soon".

Acceptance (Gherkin)
  @spec-iam-1  Scenario: a member lists the applications of a realm
    Given a running FerrisKey deployment and a member who can view instances
    When the console asks for `applications.list` on realm "master"
    Then it gets 202 with a request id, then 200 once with an envelope the browser opens into the page, then 410

  @spec-iam-2  Scenario: the control plane never holds content
    Given a finished request
    Then the stored value is an envelope, and decoding it without the browser's key yields nothing

  @spec-iam-3  Scenario: a client's secret never leaves the realm
    Given a confidential application with a secret
    When it is listed or read
    Then the result has no `secret` field

  @spec-iam-4  Scenario: an envelope belongs to its request
    When an envelope sealed for request A is opened as request B
    Then opening fails

  @spec-iam-5  Scenario: a request outside the whitelist is refused
    When a request names an operation that does not exist
    Then it is answered 400 and nothing is recorded

  @spec-iam-6  Scenario: a weak or wrong key is refused
    When the sealing key is not RSA or under 2048 bits
    Then it is answered 400

  @spec-iam-7  Scenario: rights and deployment kind
    When a member without VIEW_INSTANCES asks, or the deployment is not FerrisKey
    Then it is answered 403, or refused as other FerrisKey-only features are

  @spec-iam-8  Scenario: every request is audited without its result
    Then the organisation's audit trail shows who asked what on which realm, and no content

  @spec-iam-9  Scenario: an unfetched result expires
    When 5 minutes pass without a fetch
    Then the envelope is deleted and the request answers 404

  @spec-iam-10  Scenario: a redelivered action runs once
    When the same request id reaches the operator twice
    Then FerrisKey is called once

  @spec-iam-11  Scenario: a result too large is refused, not cut
    When the sealed result would exceed 512 KiB
    Then the request ends Failed with a message, and a page never holds more than 50 objects

  @spec-iam-12  Scenario: the console shows the applications
    Given a realm with applications
    When a member opens Identity → Applications
    Then the table shows them, search narrows them, next page loads more, and the tab is no longer marked Soon

Frozen contracts
  Sealing key = public JWK { kty: "RSA", n, e, alg: "RSA-OAEP-256" }, at least 2048 bits.
  Envelope = { v: 1, alg: "RSA-OAEP-256+A256GCM", ek: base64url(RSA-OAEP-SHA256(aes_key)), iv: base64url(12 bytes), ct: base64url(AES-256-GCM(json, aad = request_id)) }.
  POST /organisations/{o}/deployments/{d}/iam/requests  { realm, operation: { type: "applications.list", page?: u32 (default 1), limit?: u32 (1..=50, default 25), search?: string } | { type: "applications.get", id: uuid }, sealing_key } → 202 { data: { request_id } }.
  GET  /organisations/{o}/deployments/{d}/iam/requests/{request_id} → 202 pending | 200 { data: { envelope } } once | 410 delivered | 404 expired | 422 { message } when Failed.
  Result of applications.list = { items: [ApplicationSummary], next_page?: u32 }; applications.get = ApplicationDetail.
  ApplicationSummary = { id, client_id, name, enabled, client_type, public_client, service_account_enabled, protocol, registration_source, created_at }.
  ApplicationDetail = ApplicationSummary + { direct_access_grants_enabled, require_pkce, token_exchange_enabled, consent_required, redirect_uris: [string], access_token_lifetime?, refresh_token_lifetime?, id_token_lifetime?, updated_at }. No `secret`.
  Action `deployment.iam.request` v1, routing key `deployment.iam.request`, payload JSON = { deployment_id, namespace, request_id, realm, operation: { type: "applications.list", page, limit, search? } | { type: "applications.get", id }, sealing_key: <JWK>, expires_at: RFC 3339 }.
  Outcome JSON, published by Genesis and relayed unchanged by Herald to the report-outcome endpoint = { deployment_id, kind: "iam", request_id, phase: "Done" | "Failed", message?, envelope? }; `phase`, `message` and `deployment_id` are the fields the endpoint already has, `request_id` and `envelope` are new. At-least-once: the control plane ignores an outcome for a request already Done, Failed or Delivered.
  Envelope details: base64url without padding everywhere; `ct` = AES-256-GCM ciphertext followed by its 16-byte tag (what both WebCrypto and the Rust `aes-gcm` crate produce); RSA-OAEP with SHA-256 for both the hash and MGF1, empty label; AAD = the request id as its lowercase hyphenated UUID text, UTF-8.
  CRD: spec.iamRequests[] { requestId, realm, operation (JSON string), sealingKey (JSON string), expiresAt }; status.iam.requests[] { requestId, phase, message? }. Secret `<instance>-iam-results`, key `<requestId>` = envelope JSON.

Risks / open questions
  - Latency: with Herald at 15 s a request takes 15 to 30 s; the chart change to 3 s must land with or before WS-3. Owner: whoever merges WS-2.
  - FerrisKey's `search` on clients: the parameter exists; which fields it matches is not verified. Owner: WS-2, before the operator maps it.
  - A Secret key per request: cleanup after outcome must be tested against a crash between publish and delete. Owner: WS-2.
  - Showing `agent-*` clients with a badge is a default, not a decision.
