# Webhooks on a deployment

Goal
  A customer manages the webhooks of their FerrisKey deployment from the Autharie console: which realm and events, where to send them, the signing secret, and what happened to each delivery.

Context
  FerrisKey (since 0.9.0) has webhooks per realm: CRUD under `/api/realms/{realm}/webhooks`, about fifty event types, HMAC-SHA256 signing (`x-ferriskey-signature` over `"{timestamp}.{body}"`), retries with backoff, a delivery record per event with manual retry, and SSRF protection. The secret is generated by FerrisKey and returned only by `POST .../webhooks/{id}/secret/rotate`. Today a customer can only reach this through the FerrisKey admin console.
  The control plane never talks to an instance: everything goes through the data plane (actions → Genesis → IdentityInstance → operator → FerrisKey admin API, and back through Genesis' outcomes → Iggy → Herald → control plane). Branding (`deployment.iam_settings`) already follows this path; webhooks follow it too, which keeps them working for every distribution, customer cloud included. ADR 0007.

Glossary
  Webhook: one FerrisKey webhook in one realm of one deployment, managed by Autharie. Rejected: "hook", "endpoint" (the URL is the endpoint).
  Managed webhook: a FerrisKey webhook whose name starts with `autharie:` followed by the Autharie webhook id. The operator only ever touches managed webhooks; anything else in FerrisKey is the customer's own and is left alone.
  Delivery: one FerrisKey delivery record (one event to one webhook, with its attempts).
  Signing secret: the secret FerrisKey signs deliveries with.

Invariants
  - The operator never creates, changes or deletes a FerrisKey webhook that is not managed.  [test]
  - A signing secret never appears in an action payload, the IdentityInstance resource, a log line, or the control plane database in clear. It travels data plane → control plane in an outcome and is stored encrypted with the existing envelope encryption.  [test + review]
  - Custom header values are stored encrypted in the control plane and travel to the data plane in a Kubernetes Secret, never in the IdentityInstance resource.  [test]
  - A deployment holds at most `Plan::max_webhooks()` webhooks (Free: 5; paid plans: 25).  [type: limit from the plan; test]
  - The desired set of a deployment's webhooks is sent whole, so a redelivered or reordered action converges to the latest set (the action carries a monotonically increasing `revision`; Genesis ignores an older revision than the one applied).  [test]
  - Only `https://` endpoints are accepted; FerrisKey's own SSRF checks stay the last word.  [type: `WebhookEndpoint::parse`]
  - Event names are FerrisKey's, validated against a list the control plane ships; an unknown name is refused, not passed through.  [type: `WebhookEvent`]
  - Viewing webhooks and deliveries needs VIEW_INSTANCES; creating, changing, deleting, rotating, revealing a secret and retrying need MANAGE_INSTANCES. Revealing a secret is written to the organisation's audit trail.  [test]

Out of scope
  - Keycloak deployments (FerrisKey only; the console hides the tab for other kinds).
  - Per-webhook retry policy (FerrisKey's realm and system defaults apply).
  - Events the control plane itself emits (deployment created, backup failed...). These are Autharie's own events, a separate feature.
  - A "send test event" button (FerrisKey has no ping route).

Design
  Control plane (libs/autharie-domain/src/webhooks/, persistence in libs/autharie-postgres, API in libs/autharie-api)
    - `Webhook { id, deployment_id, realm, name, description, endpoint: WebhookEndpoint, events: Vec<WebhookEvent>, headers: Vec<HeaderName> (names only in clear), state: WebhookState, created_at, updated_at }`.
    - `WebhookState`: `Pending` (desired, not yet applied) | `Active { ferriskey_id }` | `Failed { reason }`; plus `secret: Option<SecretRecord { version, encrypted, received_at }>`.
    - Table `deployment_webhooks` (+ encrypted header values, encrypted secret). Migration.
    - Every change records action `deployment.webhooks` (v1) with the whole desired set and a new `revision`.
    - Rotation records action `deployment.webhook.rotate_secret` (v1) `{ webhook_id }`; the secret's `version` increments when the new one is received.
    - Retry records action `deployment.webhook.retry_delivery` (v1) `{ webhook_id, delivery_id }`.
    - Ingests outcomes (see Frozen contracts): per-webhook state, new secrets, realm list.
    - Deliveries: served from the log index (Quickwit), where Herald writes them.
  Data plane
    - Genesis: handlers for the three actions. `deployment.webhooks` writes `spec.webhooks` on the IdentityInstance and the header values into Secret `<instance>-webhook-headers` (keys `<webhook id>.<header name>`). Rotation and retry write request entries (`spec.webhookRequests`) the operator consumes idempotently by id. The status watcher publishes webhook outcomes when `status.webhooks` or `status.realms` change, reading new secrets from Secret `<instance>-webhook-secrets` (key `<webhook id>`).
    - Operator: reconciles `spec.webhooks` against FerrisKey for FerrisKey instances (create, update, delete managed webhooks; after a create, rotate once to obtain the secret), executes `spec.webhookRequests`, writes the secret into `<instance>-webhook-secrets`, reports `status.webhooks[]` and `status.realms`. Uses the instance's admin credentials as branding does.
    - Herald: relays the new outcomes; polls the deliveries of managed webhooks every cycle (per deployment that has webhooks) using a view-only FerrisKey client the operator creates in the master realm (`autharie-herald`, ViewWebhooks), and ships them to the organisation's log index as documents of kind `webhook_delivery`.
  Console
    - New deployment tab "Webhooks" (FerrisKey only): list, create/edit form (realm, name, description, endpoint, events grouped by resource, custom headers), state badge (Pending/Active/Failed), reveal signing secret (with copy, audited), rotate, delete; per webhook a deliveries view (status, event, attempts, last response code, time) with retry.

Acceptance (Gherkin)
  @spec-wh-1  Scenario: a member creates a webhook and receives its secret
    Given a running FerrisKey deployment
    When a manager creates a webhook on realm "master" for "user.created" to an https endpoint
    Then the webhook is Pending, then Active with a FerrisKey id
    And its signing secret can be revealed once received, and the reveal is audited

  @spec-wh-2  Scenario: unmanaged webhooks are left alone
    Given a FerrisKey webhook created by hand in the instance
    When the deployment's managed webhooks are reconciled
    Then the hand-made webhook still exists unchanged

  @spec-wh-3  Scenario: deleting a webhook removes it from FerrisKey
  @spec-wh-4  Scenario: rotating the secret replaces it and bumps its version
  @spec-wh-5  Scenario: a Free deployment cannot hold a sixth webhook (409, limit error)
  @spec-wh-6  Scenario: an http:// endpoint or an unknown event is refused (400)
  @spec-wh-7  Scenario: deliveries appear in the console and a failed one can be retried
  @spec-wh-8  Scenario: a viewer sees webhooks and deliveries but cannot reveal, rotate, change or retry (403)
  @spec-wh-9  Scenario: an older `deployment.webhooks` revision redelivered after a newer one changes nothing
  @spec-wh-10 Scenario: header values never appear in the IdentityInstance or an action payload

Simulation
  No. Ordering is handled by revisions and idempotent request ids, tested directly.

Workstreams
  W1 CRD and operator: `spec.webhooks`, `spec.webhookRequests`, `status.webhooks`, `status.realms`; reconcile; secrets Secret; Herald's view-only client. Owns libs/autharie-crds, libs/autharie-operator-core, chart CRDs and RBAC.
  W2 Genesis: the three handlers, header Secret, watcher outcomes. Owns libs/genesis-core. Depends on W1's CRD types.
  W3 Herald: relay outcomes, poll and index deliveries. Owns libs/herald-core, apps/herald. Depends on W1 (client Secret name) and the outcome contract.
  W4 Control plane: domain, storage, migration, encryption, API, outcome ingestion, audit, limits, deliveries search. Owns libs/autharie-domain, -core, -postgres, -api, .sqlx, openapi.json. Depends on contracts only.
  W5 Console: Webhooks tab. Owns apps/console. Depends on W4's API (regenerate client).
  Order: W1 and W4 in parallel; then W2, W3, W5; end-to-end on k3d last.

Risks / open questions
  - The secret crosses the data plane bus (Iggy, in-cluster) on its way out. Accepted: it is the instance's own secret, Iggy is not exposed, and the alternative is the control plane holding instance admin credentials. Owner: W2/W4.
  - Header values are in the `deployment.webhooks` action row in the control plane database until actions are purged. Owner: W4 — redact `headers` from the stored payload once the action is published.
  - FerrisKey has no external id on a webhook; the `autharie:<id>` name prefix is the marker. A customer renaming a managed webhook in FerrisKey's console turns it into an unmanaged one and the operator creates a new managed one. Accepted, documented.
